01 定義 / What is a harness

ハーネスエンジニアリングとは

プロンプトエンジニアリングとコンテキストエンジニアリングを包含する、上位概念。「何を言うか」ではなく「AIがどんな環境で、どこまで動けるか」を設計する領域として、2026年に公式化された。

ループエンジニアリングLoop Engineering

2026年6月、Anthropic社Claude Code開発者Boris ChernyとPeter Steinbergerの投稿から広まり、Andrew Ngが「3つの入れ子フィードバックループ」として定式化した概念。

ハーネスエンジニアリングHarness Engineering

AIの行動・権限・環境そのものを設計する。フック、ワークフロー、評価、隔離、配布までを含む。

コンテキストエンジニアリングContext Engineering

必要な文脈だけを、必要なときに供給する。

プロンプトエンジニアリングPrompt Engineering

依頼の書き方を磨く。

02 構築 / Execution flow

準備は直列、生成だけ並列、評価が先頭へ戻る

ひとつの依頼は、3つの局面を経て動く。監督モデルは実装をせず、分析・分配・最終判定だけに専念する。

01準備(直列)

  • 曖昧な依頼をカスタムコマンドで役割・文脈付きの指示書へ変換
  • 約100本の文書からルーターが該当分だけを選定

02生成(並列)

  • 複数ワーカーが識別番号付きで同時修正、コンフリクトなし
  • スタイル・型・importをフックが機械検査
監督分析→プラン→分配→最終判定
主力ワーカーシニア相当・実装本体
検証ワーカーミドル相当・検証+フォールバック
軽量ワーカージュニア相当・UI/スタイル

03採点・学習

  • 結果を基準判定・回帰テストで自動採点
  • 全ツール呼出をJSONL traceで記録

自己改善ループ — 評価結果とフィードバックが次の依頼に反映され、同じミスを繰り返さない

03 構築 / Guardrails

フック25個 — AIの行動をコードで強制する

レビューで指摘するより先に、誤ったコードがそもそも入らない状態をつくる。実行前後の4局面に検査を配置した。

Prompt

入力前処理

  • 冗長表現を削り出力を圧縮、トークン約65%削減
  • 会話が長期化して文脈が圧縮されても重要ルールを保持
Pre

実行前ブロック

  • 危険なgit・rm系6種を遮断
  • 未コミット時のcheckoutを遮断
  • 新規ファイルにヘッダー必須
  • ワーカーをworktree隔離
Post

実行後検証

  • any・セミコロン・ダブルクォートを禁止
  • 階層をまたぐ相対importを禁止
  • 自動整形と文書同期リマインド
  • 全ツール呼出をJSONL記録
Stop

終了処理

  • セッション終了時に自動採点を実行
  • 完了を通知

04 構築 / In practice

未コミットの作業を、checkout一つで消させない

ワーカーはworktreeで隔離されていても、未コミットのままcheckoutすれば、積み上げた成果はそのまま消えてしまう。フックが実行前に止め、AIは選択肢を提示して判断を人に返す。

05 構築 / Context routing

文書は約100本。全部は読ませない

文脈は量より、精度がものを言う。ルーター文書が作業内容に応じて該当文書だけを選び、無駄な文脈を積ませない。

Routing

読む文書を機械的に決める

  • ルート規約が「必ず読む文書」を宣言
  • 作業域ごとのルーターが該当文書だけをReadさせる
  • 作業域外の文書は読ませない — 文脈汚染とトークン浪費を同時に防ぐ
Skills

定型作業をコマンド化

  • マルチエージェント修正チームの自動実行
  • 別ベンダーのモデルを併用するクロスレビュー
  • 作る前に質問を重ね要件と設計を固める設計対話
  • 曖昧な依頼を役割・文脈付きの指示書へ変換
prompt refinement
入力 売上分析をするダッシュボード作って 出力 <role>売上分析を担当するフロントエンド開発者</role> <context>既存UIに準拠・月次売上データを可視化</context> <instructions>① 集計 → ② グラフ化 → ③ フィルタ追加</instructions> <output_format>既存コンポーネント構成に合わせる</output_format>

06 構築 / Evaluation

eval36ケース — ハーネス自体を回帰検証する

モデルが更新されると、これまで効いていたルールが急に効かなくなることがある。ハーネスがまだ有効かどうかを、自動で確かめる検査を持たせた。

style-any-block対象内のany使用を検出して遮断
style-any-outside-skip対象外ファイルはスキップ
style-unknown-block一般的なunknown型を遮断
style-semicolon-blockセミコロンを遮断
style-dq-ts-block.tsのダブルクォートを遮断
style-dq-tsx-import-block.tsxのimport文のみ遮断
style-dq-tsx-jsx-allowJSX属性のダブルクォートは許可
style-barrel-blockバレルimportを遮断
style-clean-passクリーンなコードは通す
import-alias-block階層をまたぐ相対importを遮断

「遮断すべきものを遮断するか」だけでなく「通すべきものを通すか」まで検査する。過剰に遮断すれば開発体験が壊れるため、許可側のケースも同数用意した。

07 構築 / Self-improving loop

instinct — 指摘を覚えて、次は先回りする

作業を見て覚え、繰り返しをルール化し、次の依頼で先回りする。同じ円を回すほど「指摘」は減り、「精度」は上がる。

01 観察

見る・覚える

どのファイルをどう直したか、クセや好みを自動で記録

02 抽出

ルール化

「いつも指摘される点」を自動でルールに変換

次の作業に反映し、同じ指摘を繰り返さない

13 課題 / Open problems

数字の裏にある、2つの未解決

導入の効果は出た。ただし「誰にでも効いた」わけではないし、「量が増えた=価値が増えた」とも言い切れない。

Issue 01

効果が一人に集中している

  • チーム全体の増加分のうち、約85%が構築者本人に由来する
  • 要因は「要件の言語化」の差と見ている。ハーネスは要件を切り出せる人の生産性を強く押し上げる
  • 確たる原因はなお調査中。オンボーディング文書は配布済みで、単なる不慣れでは説明がつかない
Issue 02

量では成果を測れない

  • コミット数・行数は活動量であって価値ではない
  • 大量生成はレビュー負債を増やすこともある
  • アウトプットが偏っている以上、費用対効果は現状読みにくい

次の一手 — 各自が要件 → 生成 → 検証を、小さなタスクからend-to-endで担当する。AIが補助しながら任せる範囲を段階的に広げ、個人依存を構造ごと解消していく。

14 今後 / Next

「生成」から「検証」へ

エージェントが大量のコードを自律的に生み出すようになり、人のレビューがボトルネックになった。関心の中心は、生成から検証へ移りつつある。

着手済み

危険なコードを自動で見つける

  • 認証情報の漏れやセキュリティの穴をAIが自動検出
  • よく出る指摘を学習させ、レビュー前に自動で防ぐ
  • 保存した瞬間に誤りや重複を検査し、その場で止める
次のアクション

CI/CD + 自動テスト

  • コードを共有すると検査とテストが自動で走る
  • 「前まで動いていた機能が壊れていないか」を機械が毎回チェック
  • 検証を人の集中力に依存させない
